# YOLOps-Agent 项目实现与架构总览

这份文档是项目里唯一保留的详细说明文档。

用途很明确：

- 需要快速理解这个项目到底做了什么
- 需要知道前后端主要模块怎么分
- 需要知道核心链路和接口边界
- 需要知道当前版本的不足和后续可扩展方向

不再额外维护多份“功能实现说明 / 接口对接说明 / 模块细节说明 / 架构书 / 项目说明书”。

## 1. 项目定位

YOLOps-Agent 是一个面向目标检测流程的轻量化 YOLOps 工作台，覆盖数据集管理、标注浏览、训练任务、模型归档和 Agent 分析。

当前定位是：

- 实习作品
- 单机演示项目
- 工程闭环展示

不是：

- 多租户系统
- 生产级任务调度平台
- 完整商业化部署产品

这个定位很重要，因为很多设计取舍都基于它，比如默认保留 SQLite、训练任务仍在后端进程内执行、文档以演示和维护为优先。

## 2. 当前技术栈

- 前端：Vue 3 + Vite
- 后端：FastAPI
- 数据库：SQLite 默认，PostgreSQL 可切换
- 模型训练：Ultralytics YOLO
- 资源存储：本地磁盘

项目是典型的前后端分离结构，但最终交付更适合走“前端构建后由后端托管”的本地一体化路线。

## 3. 当前实现的核心功能

### 3.1 数据集与标注

- 数据集创建、导入、版本管理
- YOLO 格式图片和标签读取
- 数据集预览页逐图浏览
- 标注工作台查看和编辑框
- 标注进度追踪
- 标注完成后拆分为 train / val / test

### 3.2 训练与模型

- 在全局或项目内创建训练任务
- 展示训练状态、进度、指标
- 训练完成后归档模型产物
- 模型列表查看和管理
- 模型与训练记录、项目之间建立关联

### 3.3 Agent 分析

- 基于项目上下文分析训练、模型和数据集
- 支持会话和对话记录
- 支持引用训练、模型、数据集信息
- 输出后续建议或训练计划

## 4. 核心业务链路

最重要的一条链路是：

项目 -> 数据集 -> 标注 / 预览 -> 训练 -> 模型 -> Agent 分析

展开后可以理解成：

1. 创建项目
2. 导入数据集或新建标注数据集
3. 在预览页和标注页处理图片与标签
4. 将可用数据用于训练
5. 把训练结果归档为模型
6. 在项目、模型、Agent 页面继续分析和复盘

这个链路是项目演示价值的核心，后续优化也应优先服务这条链路。

## 5. 前后端结构

### 5.1 前端

前端职责主要是工作台式页面组织和状态展示，重点页面包括：

- 全局概览
- 数据集页
- 数据集预览页
- 标注工作台
- 训练列表与训练详情
- 模型列表
- 项目列表与项目详情
- Agent 对话页

当前前端更像一个面向工程流程的操作台，不是营销官网，也不是重视觉展示型产品。

### 5.2 后端

后端职责主要是：

- 管理项目、数据集、训练、模型等业务数据
- 调用 YOLO 训练和评估
- 维护文件路径与元数据关系
- 向前端暴露统一 API
- 为 Agent 提供上下文和工具查询能力

## 6. 关键模块划分

按职责看，后端可以分成这几块：

- `app/api/`
  - 对外 API 路由
- `app/dataset/`
  - 数据集导入、统计、版本元数据、质检
- `app/annotation/`
  - 标注读写、预标注、修订历史
- `app/training/`
  - 训练调度、评估、产物收集
- `app/registry/`
  - 模型归档和版本管理
- `app/agents/`
  - Agent 对话、上下文构建、工具调用
- `app/core/`
  - 配置、数据库、路径、基础设施

前端主要按页面和 API 模块划分：

- `src/pages/`
  - 页面级视图
- `src/components/`
  - 复用组件
- `src/api/`
  - 前端 API 封装
- `src/layouts/`
  - 应用布局

## 7. 接口边界和对接原则

这个项目不需要把所有接口文档单独展开成一本书，但需要明确几个边界：

- 前端只通过 `src/api/*.js` 调接口
- 页面层不直接散写 `fetch`
- 后端负责业务校验和状态更新
- 图片、标签、模型文件本体在磁盘，数据库保存元数据和关联关系

最核心的接口类型有四类：

- 数据集与标注接口
- 训练与评估接口
- 模型与项目接口
- Agent 会话与分析接口

## 8. 数据和资源是怎么组织的

项目里的大图片、标签、训练产物和模型权重，主要在磁盘上。

数据库里主要放的是：

- 项目
- 数据集版本
- 图片索引
- 标注状态
- 训练记录
- 模型记录
- Agent 会话和计划

所以这个项目不是把所有图片“塞进数据库”或“一次性全塞进内存”。

简单理解：

- 磁盘负责存大资源
- 数据库负责存关系和索引
- 内存负责当前请求或当前页面临时处理的数据

## 9. 当前版本的主要优点

- 链路完整，适合演示
- 前后端和训练流程已经打通
- 数据集、训练、模型、项目之间已有明确关联
- 相比单纯 YOLO demo，更像一个真实工程工作台

## 10. 当前版本的主要不足

### 10.1 性能体验

- 页面切换和任务创建后的刷新仍有白屏等待
- 部分页面的缓存、预取、局部刷新策略还不统一
- 一些页面信息层级虽然比之前好，但还可以更收敛

### 10.2 架构能力

- 训练和评估仍是进程内任务，不是独立 worker
- 不适合高并发或多人长期共用
- 权限、审计、多用户隔离还不完整

### 10.3 工程化

- 自动化测试覆盖不足
- 缺少正式 migration 体系
- 缺少发布前自动检查和 CI

## 11. 推荐的后续优化顺序

如果后续还有时间，建议按下面顺序做：

1. 统一前端缓存、刷新、局部 loading 策略
2. 收紧项目名、训练名、模型名的命名规范
3. 把训练 / 评估任务逐步拆成独立 worker
4. 补数据库迁移和基础测试
5. 再整理最终打包与交付
