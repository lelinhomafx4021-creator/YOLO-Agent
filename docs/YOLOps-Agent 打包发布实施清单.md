# YOLOps-Agent 打包发布实施清单

## 目标

把当前项目整理成一个最终用户可运行的 Windows 发布版，并为后续 GitHub Release 做准备。

这里不走复杂路线，不先做 Electron，不先做公网部署，不先追求单文件 `exe`。

我们走最稳、最高效的一条线：

1. 前端构建后挂到后端
2. 后端默认使用 `SQLite`
3. 本地形成“一体化浏览器版”
4. 再打包成 Windows `exe`
5. 最后放到 GitHub Release

---

## 一句话理解

你们最终交付的软件，本质上是：

- 一个本地启动的 FastAPI 程序
- 它同时提供前端页面和后端 API
- 用户双击启动后，浏览器自动打开界面

所以不是先做“公网网站”，而是先做“本地一体版”。

---

## 总清单

### 第一阶段：先统一发布形态

目标：用户最终只启动一个东西。

要做的事：

1. 明确发布版入口只有后端
2. 前端不再依赖开发服务器
3. 前端页面改为由 FastAPI 直接提供
4. 确认启动后浏览器能打开首页

完成标准：

- 不用 `npm run dev`
- 不用手动分别开前后端
- 只启动后端就能访问完整页面

---

### 第二阶段：前端挂到后端

目标：让发布版不再依赖 Vite 开发服务。

要做的事：

1. 在 `frontend` 执行一次构建
   ```powershell
   npm run build
   ```
2. 得到前端静态产物，一般是 `dist/`
3. 在 FastAPI 中挂载静态目录
4. 处理首页路由，让访问根路径时返回前端首页
5. 处理刷新问题，避免前端路由刷新 404

为什么这一步最关键：

- 发布时不能让用户再跑前端开发服务器
- 只有先把前端静态化，后面才谈得上打包

完成标准：

- 启动后端后，浏览器访问本地地址能打开前端页面
- 页面中的 API 请求仍然正常
- 刷新页面不会直接报错

---

### 第三阶段：发布默认切换到 SQLite

目标：让最终用户不需要单独安装 PostgreSQL。

要做的事：

1. 确认后端已经支持 `SQLite`
2. 给发布版准备默认配置，优先使用 `SQLite`
3. 确认首次启动时数据库文件可自动创建
4. 确认建表和轻量迁移在 `SQLite` 下正常
5. 确认数据目录、配置目录、数据库文件路径清晰

为什么这样做：

- 教学软件最怕环境门槛高
- `SQLite` 更适合单机交付
- 更适合 GitHub 直接下载使用

完成标准：

- 新机器上不装 PostgreSQL 也能跑
- 首次启动后自动生成 `db` 文件
- 基本页面和核心功能能正常工作

---

### 第四阶段：做本地一体版验证

目标：先别急着打包，先确认“发布逻辑”本身成立。

要做的事：

1. 关闭前端开发服务器
2. 只启动后端
3. 用浏览器访问本地地址
4. 验证关键页面和 API
5. 验证静态文件、上传、导出、数据写入路径

优先验证这些能力：

- 首页能打开
- 数据集页面能打开
- 标注页面能打开
- 设置页面能打开
- API 请求没有跨域问题
- 基础数据能正常保存

为什么先做这一步：

- 如果一体版没跑通，打包也只是把问题一起打进去

完成标准：

- 这套程序已经可以当“未打包的发布版”使用

---

### 第五阶段：补一个真正的发布入口

目标：给打包准备一个稳定的程序入口。

不要直接拿开发命令打包，例如：

```powershell
uvicorn app.main:app --reload --host 127.0.0.1 --port 8009
```

应该做一个单独入口，例如：

- `backend/run_app.py`

这个入口负责：

1. 读取配置
2. 检查端口
3. 初始化目录
4. 启动 FastAPI
5. 自动打开浏览器
6. 输出日志

完成标准：

- 双击或执行这个入口，就能启动完整系统

---

### 第六阶段：先打包成 onedir 版本

目标：优先得到稳定发布包，而不是追求最花哨的形式。

推荐工具：

- `PyInstaller`

推荐形式：

- `onedir`

不建议一开始追求：

- `onefile`
- 单文件 `exe`

原因：

- 你们项目有前端静态资源、模型依赖、动态图像处理和 Python 运行时
- `onedir` 更稳定，也更容易查错

建议动作：

1. 用 `PyInstaller` 打包发布入口
2. 把前端静态资源一起带进去
3. 把运行所需目录一并整理到输出目录

完成标准：

- 输出一个完整的 Windows 发布目录
- 目录中双击主程序即可运行

---

### 第七阶段：整理发布目录

目标：让产物结构清晰，方便测试和发布。

建议目录形态：

```text
YOLOps-Agent-win-x64/
  YOLOps-Agent.exe
  _internal/
  data/
  logs/
  README.txt
```

其中建议明确：

- `data/`：业务数据
- `logs/`：日志
- `README.txt`：启动说明

完成标准：

- 目录结构清楚
- 删除源码后，这个目录仍可单独运行

---

### 第八阶段：做手工发布测试

目标：验证打包产物是否真能交付别人使用。

建议测试方式：

1. 把发布目录复制到另一个干净目录
2. 尽量不要依赖开发环境变量
3. 模拟第一次使用
4. 重新启动几次
5. 检查日志和数据是否生成

重点检查：

- 能不能启动
- 首页能不能打开
- 前端资源有没有丢
- 数据库能不能自动建
- 写文件权限是否正常
- 端口是否冲突

完成标准：

- 在接近真实用户环境下也能运行

---

### 第九阶段：再做 GitHub Release

目标：把已经验证过的产物发出去。

正确顺序是：

1. 先本地打包验证
2. 再做 GitHub 自动化

不要反过来。

GitHub 发布建议：

1. 打版本 tag，例如 `v0.1.0`
2. 用 GitHub Actions 在 Windows 环境打包
3. 生成压缩包
4. 上传到 Release

建议先发布：

- `YOLOps-Agent-win-x64.zip`

以后稳定了再补：

- `YOLOps-Agent-Setup.exe`

完成标准：

- 用户可直接从 Release 下载并使用

---

## 最推荐的执行顺序

按效率最高的顺序做：

1. 前端 `build`
2. FastAPI 挂前端静态文件
3. 发布默认改成 `SQLite`
4. 验证本地一体版
5. 写 `run_app.py`
6. `PyInstaller --onedir`
7. 手工测试发布目录
8. GitHub Release 自动化

---

## 你们现在最该先做什么

只看当前阶段，先做前三件事：

1. 前端构建
2. 前端挂到后端
3. 默认 `SQLite`

这三件完成后，你们就已经拥有“可交付雏形”了。

之后的打包和 GitHub 发布，实际上只是把这套已成立的运行方式封装起来。

---

## 当前阶段不要分心的事

先不要做这些：

- 不要先改 Electron
- 不要先搞 Tauri
- 不要先追求单文件 `exe`
- 不要先做公网部署
- 不要先让发布版依赖 PostgreSQL

这些都不是当前最高收益路径。

---

## 用最容易懂的话总结

你们现在不是“做两个版本”，而是“先把最终运行方式跑通”。

这个最终运行方式就是：

1. 前端先编译成静态文件
2. 后端把这些页面提供出来
3. 后端自己也提供 API
4. 数据默认走 `SQLite`
5. 浏览器打开本地页面
6. 最后再把后端打成 `exe`

所以你们下一步的正确目标不是“先发 exe”，而是：

先把“本地一体版”做出来。

只要这一步通了，后面的打包和 GitHub 发布就是顺水推舟。
