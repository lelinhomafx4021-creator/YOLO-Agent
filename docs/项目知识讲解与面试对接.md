# YOLOps-Agent 项目知识讲解与面试对接

这份文档不是实现细节手册，而是收尾阶段的项目知识说明。

用途：

- 自己复盘项目时快速回忆核心知识
- 面试时把项目、部署、SQLite、Agent、YOLO 这些话题讲顺
- 避免只会说“我做了一个平台”，但说不清背后的工程判断

## 1. 这个项目到底是什么

YOLOps-Agent 是一个面向目标检测流程的轻量化工作台。

它不是单纯上传图片然后跑一次 YOLO 的 demo，而是把这些环节串起来：

- 项目
- 数据集
- 标注与预览
- 训练
- 模型归档
- Agent 分析

项目的价值在于闭环，而不在于单点功能。

## 2. 这个项目适合怎么讲

最简单的讲法：

我做了一个单机版目标检测工程工作台，用 Vue 3 + FastAPI + YOLO 跑通了从数据集管理、标注浏览、训练任务、模型归档到 Agent 分析的完整链路，重点解决的是项目、数据、训练、模型之间关系容易混乱的问题。

面试时不要把重点放在“页面很多”。

更好的重点是：

- 我为什么做这个项目
- 我把什么链路打通了
- 我做了哪些工程取舍
- 这个项目当前适合什么场景，不适合什么场景

## 3. 项目知识讲解

### 3.1 为什么不是单纯 YOLO demo

真实目标检测项目里更麻烦的通常不是“能不能训起来”，而是：

- 数据集版本怎么管理
- 标注状态怎么追踪
- 训练和模型怎么绑定
- 后续分析怎么回看

这个项目做的事情，就是把这些工程问题组织起来。

### 3.2 为什么用 Vue 3 + FastAPI

- Vue 3 适合快速搭建工作台式前端
- FastAPI 适合工具型后端，接口清楚，开发效率高
- 两者组合很适合做这种单机演示型工程项目

### 3.3 为什么数据资源主要放磁盘

图片、标签、模型权重、训练产物这些都比较大，不适合直接塞进数据库。

所以项目采用的是：

- 磁盘存资源本体
- 数据库存索引、关系和元数据

这也是很多实际工程里更常见的做法。

## 4. 部署和交付怎么讲

### 4.1 当前项目最适合的交付方式

当前最适合的是：

- 单机本地运行
- SQLite 默认交付
- 前端构建后由后端托管

这比强行做复杂分布式部署更符合项目当前定位。

### 4.2 为什么不急着做复杂部署

因为这个项目当前是实习作品和演示项目，最重要的是：

- 链路完整
- 体验可演示
- 结构清楚

而不是：

- 高并发
- 多租户
- 大规模线上任务调度

### 4.3 如果继续做，部署上会怎么升级

后续可以再逐步升级：

- 前后端一体化发布
- 独立 worker 处理训练和评估
- PostgreSQL 作为多人协作数据库
- 更正式的发布和升级流程

## 5. SQLite 和 PostgreSQL 怎么讲

### 5.1 为什么当前保留 SQLite

因为 SQLite 非常适合：

- 单机
- 本地演示
- 快速交付
- 降低环境依赖

对于实习项目，这是非常合理的工程取舍，不是“技术不够先进”。

### 5.2 PostgreSQL 还保留着说明什么

说明项目不是彻底写死在 SQLite 上，而是保留了后续扩展到正式部署形态的空间。

也就是说，这个项目当前是：

- SQLite 默认
- PostgreSQL 可切换

这种设计在面试里很好讲，因为它体现的是阶段性取舍，而不是纯粹偷懒。

### 5.3 面试里怎么回答“为什么不用 MySQL”

可以直接说：

这个项目本身并不依赖某个特定数据库生态，当前优先考虑的是单机演示和最小交付成本，所以优先保留 SQLite；如果进入多人协作或服务化部署，再切 PostgreSQL。重点不在数据库品牌，而在交付场景和工程权衡。

## 6. Agent 知识怎么讲

### 6.1 什么叫“普通 Agent”

这里的 Agent 不要讲得太玄。

在这个项目里，普通 Agent 可以理解成：

- 有上下文
- 能看项目数据
- 能围绕训练、模型、数据集输出分析结果

它不是全自动研发系统，也不是完全自主的智能体。

### 6.2 这个项目里的 Agent 做了什么

- 读取项目上下文
- 围绕训练结果、模型状态、数据集情况进行分析
- 支持会话记录
- 支持引用具体训练或模型信息
- 给出下一步建议

### 6.3 面试里怎么讲 Agent 才稳

不要上来就说“我做了 AI 智能体平台”。

更稳的说法是：

我做的是一个结合项目上下文的分析助手，它能围绕训练、模型和数据集做结构化分析，提升复盘和下一轮迭代的效率。

这样更真实，也更符合当前项目成熟度。

## 7. YOLO 知识怎么讲

### 7.1 这个项目和 YOLO 的关系

YOLO 是这个项目里训练和推理能力的核心引擎，但项目本身不等于 YOLO。

这个项目更像是：

- 用 YOLO 作为检测模型能力
- 在外层补齐数据、训练、模型、分析的工程组织

### 7.2 mAP50、mAP50-95 怎么说

- `mAP50`：IoU 阈值为 0.5 时的检测表现
- `mAP50-95`：更严格、更全面，通常更能反映定位泛化能力

如果训练集表现很好，但验证集下降明显，常见说明是：

- 过拟合
- 数据规模或分布不足
- 标注质量存在问题

### 7.3 面试里 YOLO 不要讲偏

不要把重点全放在模型参数和论文背景。

你这个项目更有价值的地方是：

- 怎么组织训练流程
- 怎么做训练记录和模型归档
- 怎么把结果返回到前端和 Agent

## 8. 高频面试问题

### 8.1 这个项目最大的亮点是什么

不是功能堆得多，而是已经形成了一个能演示、能讲清楚、能继续扩展的目标检测工程闭环。

### 8.2 当前最大的不足是什么

- 训练和评估还是进程内任务
- 前端缓存和刷新策略还不够统一
- 自动化测试和正式 migration 不完整

### 8.3 如果继续做，下一步做什么

优先顺序可以讲成：

1. 前端缓存和局部刷新
2. 训练 / 评估任务拆到独立 worker
3. 数据库迁移和测试体系补齐

## 9. 一句话收尾

这个项目最适合的讲法，不是“我做了很多功能”，而是“我把一个真实目标检测流程里的关键工程环节组织成了一个完整、可演示的工作台”。
